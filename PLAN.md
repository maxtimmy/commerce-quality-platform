# Commerce Quality Platform — план

Каждый этап завершается запуском относящихся к нему проверок и обновлением `STATUS.md`. Следующий этап начинается после устранения обнаруженных ошибок.

## Этап 1. Каркас и health smoke

**Статус:** завершён 2026-09-30.

**Результат:** структура приложения и QA-кода, Docker Compose с API/PostgreSQL/Redis, health endpoint, один независимый smoke test.

**Проверка:** контейнеры healthy; `GET /health` возвращает документированный ответ; smoke suite проходит из отдельного QA-контейнера или локального окружения.

## Этап 2. Модель данных и API каталога

**Статус:** завершён 2026-10-01.

**Результат:** миграции PostgreSQL, товары и категории, CRUD для администратора, чтение для покупателя, seed-данные.

**Проверка:** позитивные/негативные API-тесты, валидация схем, сверка API с БД, изоляция данных.

## Этап 3. Identity, JWT и RBAC

**Статус:** завершён 2026-10-01.

**Результат:** регистрация/вход, короткоживущие access tokens, роли и защищённые операции.

**Проверка:** матрица доступа, истёкшие/повреждённые/отсутствующие токены, уникальность пользователей, отсутствие утечек чувствительных данных.

## Этап 4. Inventory и конкурентность

**Статус:** завершён 2026-10-01.

**Результат:** остатки, атомарное резервирование, идемпотентность, Redis для краткоживущего состояния.

**Проверка:** конкурентные запросы, отсутствие oversell и отрицательных остатков, повтор запроса, согласованность PostgreSQL/Redis.

## Этап 5. Orders и сквозные интеграции

**Статус:** завершён 2026-10-01.

**Результат:** оформление и просмотр заказа, атомарный commit резерва, идемпотентная отмена с возвратом остатка и стабильные коды ошибок.

**Проверка:** happy path, неактивный/чужой резерв, повторная и конкурентная отправка, RBAC, отмена и сверка нескольких API с БД.

## Этап 6. OpenAPI и contract/property-based testing

**Статус:** завершён 2026-10-02.

**Результат:** актуальные схемы трёх API и Schemathesis suite из 27 проверок по операциям.

**Проверка:** отсутствие 5xx, schema/content-type conformance, property-based негативные данные и документированные исключения без скрытого отключения ошибок.

## Этап 7. Минимальный UI и Playwright

**Статус:** завершён 2026-10-04.

**Результат:** отдельный Nginx Web UI и Chromium Playwright suite для критического пользовательского пути.

**Проверка:** вход, каталог, оформление заказа, ошибки доступа/остатка, компенсационный release, desktop/mobile и клавиатура; устойчивые локаторы и независимые данные.

## Этап 8. Полный suite, Allure и параллельный CI

**Статус:** завершён локально 2026-10-04; внешний GitHub Actions QA run успешно выполнен 2026-10-05.

**Результат:** 164 содержательных теста, Allure Report 2.46.1 и матричный GitHub Actions workflow для трёх браузеров.

**Проверка:** `--collect-only`, повторные прогоны, три браузера, failure artifacts, HTML-отчёт и actionlint; публичный QA run 37310015364 завершён успешно.

## Этап 9. Performance и DAST

**Статус:** завершён локально 2026-10-05; внешний ручной performance/DAST run пока не запускался.

**Результат:** смешанный Locust-профиль 20 users / 2 min, безопасные OWASP ZAP Web/OpenAPI scans и ручной nonfunctional workflow.

**Проверка:** guardrails и контролируемый failure path, полная очистка load-данных, четыре DAST-отчёта с triage, повтор функциональных suites и actionlint; показатели не выдаются за production SLA.

## Этап 10. Документация и финальная воспроизводимость

**Статус:** завершён локально 2026-10-05; репозиторий готов к будущей публикации, но не опубликован.

**Результат:** английский портфолио-README, сохранённая русская версия, MIT License и однокомандный чистый audit в изолированном Compose-проекте.

**Проверка:** сборка без кэша, чистая миграция и seed, все suites и три браузера, Allure/Locust/ZAP, отсутствие остаточных данных, локальные ссылки, Compose/actionlint и удаление audit volume.
