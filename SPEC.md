# Commerce Quality Platform — спецификация

## 1. Назначение

Публичный воспроизводимый QA-стенд минимального микросервисного интернет-магазина. Проект должен подтверждать практические навыки Junior QA / API QA / QA Automation и оставаться достаточно компактным, чтобы основным результатом был QA-код, а не разработка магазина.

## 2. Границы проекта

### Тестируемое приложение

Минимальные домены:

- identity: регистрация, вход, JWT, роли `customer` и `admin`;
- catalog: товары и цены;
- inventory: остатки и конкурентное резервирование;
- orders: оформление и просмотр заказов;
- web: небольшой пользовательский путь «вход → каталог → заказ».

На первом этапе приложение представлено одним API-контейнером с health endpoint. Домены будут выделены в отдельные сервисы только там, где это создаёт полезные интеграционные границы для тестирования.

### QA-код

QA-код хранится отдельно от приложения и включает:

- Pytest + requests для API и интеграционных проверок;
- Playwright для критических UI-путей;
- Schemathesis для OpenAPI contract/property-based testing;
- прямые проверки PostgreSQL и Redis;
- Locust для нагрузки;
- OWASP ZAP baseline для DAST;
- Allure-отчёты и GitHub Actions.

+-------------------+       +-------------------+  +-------------------+
| Identity / Catalog|       | Orders            |  | Inventory         |

+---------+---------+       +---------+---------+  +---------+---------+

  api/  integration/  ui/  contract/  load/  security/

Начальное объединение identity/catalog в компактный сервис допустимо. Границы orders и inventory нужны для реалистичных интеграционных и конкурентных сценариев. PostgreSQL — источник истины, Redis — кэш и/или краткоживущие резервы.

## 4. Проверяемые требования

1. Стенд запускается одной командой Docker Compose на чистом окружении с Docker.
2. API публикует OpenAPI и имеет health/readiness endpoints.
3. JWT-аутентификация и RBAC проверяются позитивными и негативными сценариями.
4. Повторные и конкурентные операции с остатками не создают отрицательный остаток и не оформляют больше товара, чем доступно.
5. Ключевые ответы API сверяются с PostgreSQL; поведение кэша проверяется отдельно.
6. Тестовые данные изолированы и очищаются воспроизводимо.
7. Suites разделены минимум на `smoke` и `regression`.
8. CI выполняет независимые группы тестов параллельно и публикует Allure-артефакты.
9. Locust содержит документированные сценарии и критерии оценки, ZAP выполняет baseline-проход.
10. Итоговый suite содержит не менее 150 содержательных собранных проверок. Параметризация не используется только ради увеличения числа.

## 5. Критерии качества и честность результатов

- В зачёт идут только тесты, обнаруженные командой сбора Pytest/Playwright и имеющие самостоятельную проверяемую цель.
- README приводит только фактически воспроизведённые команды и результаты с указанием окружения и даты.
- Проект не заявляет production-нагрузку, реальных пользователей или бизнес-эффект.
- Для нагрузочных тестов фиксируются профиль, длительность, окружение и сырые отчёты; результаты не обобщаются за пределы стенда.
- Известные ограничения и нестабильные проверки указываются явно.

## 6. Критерий готовности всего проекта

Все сервисы поднимаются с нуля, обязательные suites проходят, число собранных содержательных проверок ≥150, Allure/Locust/ZAP создают воспроизводимые артефакты, CI-конфигурация валидна, а README позволяет третьему лицу повторить запуск и понять тестовую стратегию.

## 7. Реализованный интерфейс каталога

Базовый префикс: `/api/v1`.

- `/categories`: создание и список; `/categories/{id}`: чтение, частичное обновление и удаление.
- `/products`: создание и список; `/products/{id}`: чтение, частичное обновление и удаление.
- Список товаров поддерживает `limit`, `offset`, `category_id`, `is_active` и `search`.
- Изменяющие операции доступны только пользователю с ролью `admin`; чтение остаётся публичным.
- Используются HTTP 201/200/204 для успешных операций, 404 для отсутствующих сущностей, 409 для конфликтов уникальности/связей и 422 для ошибок входных данных.
- `/health` проверяет процесс, `/ready` — доступность PostgreSQL и Redis.

## 8. Реализованный интерфейс Identity

- `POST /api/v1/auth/register` создаёт только роль `customer`; email нормализуется в нижний регистр, пароль хранится как Argon2-хеш.
- `POST /api/v1/auth/token` использует OAuth2 password form и выдаёт HS256 JWT на 15 минут.
- `GET /api/v1/auth/me` возвращает текущего активного пользователя.
- JWT содержит обязательные `sub`, `role`, `iat`, `exp`; отсутствующие, истёкшие и повреждённые токены возвращают 401 с `WWW-Authenticate: Bearer`.
- Локальный admin создаётся идемпотентным seed. Демонстрационные секрет и пароль из Compose не предназначены для production.
- Refresh tokens, logout, восстановление пароля, подтверждение email и rate limiting пока не реализованы.

## 9. Реализованный интерфейс Inventory

Inventory работает отдельным FastAPI-процессом на порту `8001`, но пока использует общий PostgreSQL-инстанс.

- `GET /api/v1/inventory/{product_id}` публично возвращает доступное количество.
- `PUT /api/v1/inventory/{product_id}` позволяет admin установить общее количество с учётом уже зарезервированного.
- `POST /api/v1/reservations` создаёт атомарный резерв и требует JWT и `Idempotency-Key`.
- `POST /api/v1/reservations/{id}/release` идемпотентно освобождает резерв владельцем или admin.
- PostgreSQL — источник истины; условный `UPDATE` не допускает oversell, advisory lock сериализует конкурентные повторы ключа.
- Redis хранит mapping idempotency key → reservation ID с TTL 10 минут. При недоступном Redis операции используют PostgreSQL fallback, а readiness возвращает 503.
- Автоматическое истечение и commit резервов пока не реализованы и относятся к этапу Orders.

## 10. Реализованный интерфейс Orders

Orders работает отдельным FastAPI-процессом на порту `8002` и использует общий PostgreSQL-инстанс для атомарного перехода Inventory → Order.

- `POST /api/v1/orders` создаёт заказ из активного резерва владельца и требует JWT и `Idempotency-Key`.
- При commit резерв получает статус `committed`, а зарезервированное количество атомарно вычитается из `reserved_quantity`.
- Цена товара фиксируется в заказе как `unit_price`; `total_amount` вычисляется при создании.
- Повтор того же пользователя, ключа и payload возвращает существующий заказ без повторного изменения остатка; другой payload возвращает 409.
- `GET /api/v1/orders` и `GET /api/v1/orders/{id}` доступны владельцу; admin может читать все заказы.
- `POST /api/v1/orders/{id}/cancel` доступен владельцу или admin и идемпотентно возвращает товар в доступный остаток.
- Один резерв может породить только один заказ; конкурентные commit сериализуются блокировкой строки резерва и ограничениями PostgreSQL.
- Платежи, доставка, автоматическое истечение резервов и распределённые транзакции пока не реализованы.

## 11. Реализованное contract/property-based тестирование

- Schemathesis загружает OpenAPI всех трёх API и создаёт отдельную Pytest-проверку для каждой операции.
- GET-операции получают детерминированные positive-примеры; изменяющие операции — negative-примеры, чтобы проверять валидацию без создания случайных данных.
- На каждую операцию выполняется до 10 Hypothesis-примеров.
- Проверяются отсутствие 5xx, Content-Type, соответствие документированной схеме ответа и отклонение невалидных данных.
- Дополнительные query-параметры считаются допустимыми, поскольку FastAPI в текущем стенде их игнорирует.
- `status_code_conformance` пока не включён: OpenAPI ещё не описывает все доменные ответы 401/403/404/409. Это явное ограничение, а не скрытый skip.

## 12. Реализованный Web UI

- Отдельный Nginx-контейнер публикует адаптивный статический HTML/CSS/JavaScript UI на порту `8080` и предоставляет `/health`.
- Один origin проксирует Identity/Catalog, Inventory и Orders через `/gateway/core`, `/gateway/inventory` и `/gateway/orders`; CORS в API не включён.
- Пользовательский путь включает публичный каталог, вход, reserve → order, подтверждение и список заказов, а также logout.
- JWT хранится только в `sessionStorage` и удаляется при logout или 401. Reserve и order используют независимые idempotency keys.
- Если order не создан после успешного reserve, UI выполняет best-effort release и показывает безопасную ошибку.
- Динамический API-текст выводится через `textContent`; формы имеют labels, ошибки — `role="alert"`, тесты используют стабильные `data-testid`.
- Playwright suite выполняется в Chromium, Firefox и WebKit и проверяет desktop/mobile viewport, клавиатурный вход, критический путь, ошибки остатка, компенсацию и защиту от двойного UI-действия.
- Frontend-фреймворк и отдельная бизнес-логика UI намеренно не используются.

## 13. Реализованные отчёты и CI

- `allure-pytest` формирует результаты с иерархией проект → suite → подсистема и environment metadata.
- Docker-генератор на Allure Report 2.46.1 объединяет раздельные результаты и создаёт статический HTML без установки Java/Allure на хост.
- GitHub Actions разделяет smoke, regression и contract на независимые jobs; UI использует матрицу Chromium/Firefox/WebKit.
- Каждый job работает с отдельным Compose-проектом и БД, сохраняет результаты и очищает volumes даже после ошибки.
- Итоговый CI job объединяет raw results и сохраняет HTML report как artifact на 14 дней; Pages и deployment не используются.
- Локально workflow проверяется actionlint. Успешный внешний CI run нельзя заявлять до публикации репозитория.
