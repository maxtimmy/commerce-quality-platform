# Commerce Quality Platform — спецификация

## 1. Назначение

Публичный воспроизводимый QA-стенд минимального микросервисного интернет-магазина. Проект должен подтверждать практические навыки Junior QA / API QA / QA Automation и оставаться достаточно компактным, чтобы основным результатом был QA-код, а не разработка магазина.

## 2. Границы проекта

### Тестируемое приложение

Минимальные домены:

- identity: регистрация, вход, JWT, роли `customer` и `admin`;
- catalog: товары и цены;
- inventory: остатки и конкурентное резервирование;
- orders: оформление и просмотр заказов;
- web: небольшой пользовательский путь «вход → каталог → заказ».

На первом этапе приложение представлено одним API-контейнером с health endpoint. Домены будут выделены в отдельные сервисы только там, где это создаёт полезные интеграционные границы для тестирования.

### QA-код

QA-код хранится отдельно от приложения и включает:

- Pytest + requests для API и интеграционных проверок;
- Playwright для критических UI-путей;
- Schemathesis для OpenAPI contract/property-based testing;
- прямые проверки PostgreSQL и Redis;
- Locust для нагрузки;
- OWASP ZAP baseline для DAST;
- Allure-отчёты и GitHub Actions.

```text
                         +----------------+
                         | Web storefront |
                         +-------+--------+
                                 |
          +----------------------+----------------------+
          |                      HTTP                    |
          v                                              v
+-------------------+       +-------------------+  +-------------------+
| Identity / Catalog|       | Orders            |  | Inventory         |
| API               |<----->| API               |->| API               |
+---------+---------+       +---------+---------+  +---------+---------+
          |                           |                      |
          +---------------------------+----------------------+
                                      |
                         +------------+------------+
                         | PostgreSQL | Redis      |
                         +------------+------------+

qa/
  api/  integration/  ui/  contract/  load/  security/
```

Начальное объединение identity/catalog в компактный сервис допустимо. Границы orders и inventory нужны для реалистичных интеграционных и конкурентных сценариев. PostgreSQL — источник истины, Redis — кэш и/или краткоживущие резервы.

## 4. Проверяемые требования

1. Стенд запускается одной командой Docker Compose на чистом окружении с Docker.
2. API публикует OpenAPI и имеет health/readiness endpoints.
3. JWT-аутентификация и RBAC проверяются позитивными и негативными сценариями.
4. Повторные и конкурентные операции с остатками не создают отрицательный остаток и не оформляют больше товара, чем доступно.
5. Ключевые ответы API сверяются с PostgreSQL; поведение кэша проверяется отдельно.
6. Тестовые данные изолированы и очищаются воспроизводимо.
7. Suites разделены минимум на `smoke` и `regression`.
8. CI выполняет независимые группы тестов параллельно и публикует Allure-артефакты.
9. Locust содержит документированные сценарии и критерии оценки, ZAP выполняет baseline-проход.
10. Итоговый suite содержит не менее 150 содержательных собранных проверок. Параметризация не используется только ради увеличения числа.

## 5. Критерии качества и честность результатов

- В зачёт идут только тесты, обнаруженные командой сбора Pytest/Playwright и имеющие самостоятельную проверяемую цель.
- README приводит только фактически воспроизведённые команды и результаты с указанием окружения и даты.
- Проект не заявляет production-нагрузку, реальных пользователей или бизнес-эффект.
- Для нагрузочных тестов фиксируются профиль, длительность, окружение и сырые отчёты; результаты не обобщаются за пределы стенда.
- Известные ограничения и нестабильные проверки указываются явно.

## 6. Критерий готовности всего проекта

Все сервисы поднимаются с нуля, обязательные suites проходят, число собранных содержательных проверок ≥150, Allure/Locust/ZAP создают воспроизводимые артефакты, CI-конфигурация валидна, а README позволяет третьему лицу повторить запуск и понять тестовую стратегию.
